## 2. Install the six-module production ledger before connecting monetization adapters  `🏷️ OPERATING_FRAMEWORK`

Treat content production and money movement as related but separate state machines. A published page can exist without revenue; a reported conversion can exist without an enforceable receivable; a prepaid call deposit is cash with a matching liability until the service is earned. The six modules below form one copy-pasteable Python reference when concatenated in numbered order. They use integer cents, immutable journal lines, stable source identifiers, request fingerprints, and SQLite transactions. Each worker opens its own connection against one database on supported local storage. BEGIN IMMEDIATE serializes read-check-write operations, while uniqueness constraints prevent duplicate intake and duplicate event posting. A busy timeout produces an explicit failure rather than an unlocked fallback; retry the complete request with its original key. Do not place this database on a shared network filesystem or reuse connections across worker threads. At higher write concurrency, port the same invariants to PostgreSQL using row locks and unique event keys. These guarantees cover ledger transitions, not arbitrary third-party actions. This reference records confirmed provider events and does not initiate payments, reserve live call inventory, or create an external custody service. Those adapter boundaries require their own authenticated inputs and provider-supported deduplication.

The verification and escrow vocabulary needs precise implementation. Verification means an authorized reviewer has checked evidence and contractual eligibility; it does not mean cash has arrived. The held state represents an allocated prepaid deposit confirmed at the payment provider, recorded as a liability, not a claim that the publisher operates regulated escrow. Invoice-route approval creates receivables and revenue together. Prepaid approval releases the held liability into revenue without creating a second receipt. Settlement moves an invoice receivable into cash exactly once. A rejected event never becomes revenue; a confirmed held-fund refund reverses the deposit liability and cash. The amount is fixed at intake, so submit a new corrected external record after rejecting an erroneous one rather than silently editing history. Use batch identifiers for finalized advertising statements and accepted affiliate cohorts; retain the underlying partner export outside this compact ledger. Authenticate webhook signatures, merchant account identity, currency, and statement totals before calling the posting function. If an upstream identifier is reused with changed amounts, the fingerprint mismatch stops processing. Disputed paid earnings require documented reversal entries through a separately reviewed extension, not deletion of old journal lines or relabeling a cash receipt as fresh revenue.

Build the deployment around reproducible evidence rather than confidence in a single happy-path test. The QA module exercises duplicate delivery, an altered duplicate, held funds, approval, settlement, rejection, refunds, and cash expenses against a temporary database. It also runs a two-connection duplicate-settlement test and verifies that only one cash receipt is posted. Every operation must balance to zero, every foreign key must resolve, and every final statement must reconcile cash, receivables, held liabilities, and operating result. These checks are supplied for execution; they have not been run in this chapter. In deployment, add a process-kill test between journal insertion and commit, restore a backup to a clean host, and replay authenticated events in different delivery orders. Out-of-order transitions should fail visibly and remain in the adapter's durable retry queue, never disappear as successful acknowledgments. Keep raw call records and subscriber selections in access-controlled storage with retention limits; the ledger needs opaque identifiers, not full browsing histories. If the California Consumer Privacy Act applies, map collection notices and request handling to actual identifiers and processors. A deletion workflow must distinguish removable audience attributes from records retained under an applicable statutory exception.

2. Post only accepted economics
   - Import final partner statements and apply the verified state transitions.
