## 2. Build a serialized evidence ledger before connecting partner callbacks  `🏷️ OPERATING_FRAMEWORK`

The six modules below form one small executable SQLite reference when copied in order into a Python file. They deliberately implement a narrow workflow: approved positive-value invoices, full settlement, paid operating expenses, and one currency per database. Initialize the database once before starting workers; each worker then opens its own connection on a local disk with reliable locking. Do not deploy this file on an object store or an unsuitable network filesystem. The single writer acquires BEGIN IMMEDIATE before reading mutable state, and every state change, journal entry, and idempotency result commits together. Concurrent replay therefore cannot double-recognize a case through these functions. A busy timeout fails the request without acknowledging success; the caller retries the same event identifier and identical payload. The unique partner/external identifier also stops a duplicate intake disguised with another event identifier. Authentication, authorization, signature validation, payload size limits, and secret storage belong in the adapter before these functions. Treat their absence from this compact reference as integration work, not as permission to expose a database operation directly to an unauthenticated browser or partner callback.

Intake scoring is an eligibility switch, not a speculative estimate of player value. The trusted adapter resolves rights, territory, registration scope, and operator eligibility from maintained evidence; user-supplied booleans cannot satisfy those checks. The immutable amount represents an approved commercial unit, such as a $200 accepted CPA, not the customer's deposit. Verification requires earned revenue evidence: delivered subscription service, an approved builder statement, an accepted first-time-depositor qualification, or a finalized NGR waterfall. The requested verification/escrow state machine is implemented as an evidence reserve only. Intake can become rejected or verified; verified can become released after a bank-backed match. No state holds customer funds, and released means the operator's invoice was collected. Prepaid annual subscriptions need deferred revenue and monthly service recognition, so they remain outside this monthly earned-service example. Similarly, refunds, partial payments, currency conversion, and later clawbacks require explicit compensating-entry extensions before those features are enabled. Never edit an earned amount to hide a dispute. Preserve the original record and add a separately authorized adjustment workflow with its own replay key, evidence, and balancing entries when extending the reference.

Every journal row specifies equal debit and credit cents, giving the reconciliation view a transparent bridge between revenue, expense, receivables, and cash change. Integer cents avoid binary floating-point drift; rounding occurs once when the contractual invoice is prepared. A settlement references a canonical bank receipt allocation, and its unique key prevents that allocation from funding two cases. For a bulk remittance, the adapter must first construct immutable allocation lines whose sum equals the bank receipt; this reference accepts only those prevalidated full-invoice lines. Store bank and partner evidence in restricted storage and retain references rather than sensitive raw payloads in the ledger. The supplied test exercises concurrent identical verification, altered replay rejection, settlement mismatch rollback, duplicate settlement suppression, and accounting totals. It is included as executable QA, not represented as having been run here. Before production, add process-crash recovery tests, duplicate receipt tests across separate cases, restoration drills, and authenticated adapter tests. All outward financial actions remain outside these modules: they record observed receipts and expenses rather than initiating transfers. That separation avoids pretending a database transaction can atomically commit an unrelated bank or partner API action.

**SOP — Standard Operating Procedure**

1. Authenticate and normalize the source event
   - Verify the partner signature, resolve territory evidence, and assign a stable namespaced event identifier.
   - Preserve the original restricted payload and derive deterministic invoice or conversion identifiers before calling intake.
2. Approve earned economics inside one transaction
   - Match delivered service or accepted qualification evidence, then call verify with the approved integer-cent amount already fixed.
   - Rejected leads produce no revenue; the same case cannot be recognized again under a fresh event identifier.
3. Allocate the observed bank remittance
   - Match the remittance advice to bank cash and assign immutable full-invoice allocation identifiers before calling settle.
   - Quarantine partial, duplicate, foreign-currency, or unmatched allocations rather than forcing them through this bounded workflow.
4. Close, inspect, and restore
   - Compare the reconciliation view with partner statements, paid expense evidence, and the bank statement; test backup restoration.
   - Require revenue minus expenses to equal cash change plus receivable change for this no-opening-balance reference.
