## Executive Summary

Operators sharing GPUs on Kubernetes converge on one stack: the NVIDIA GPU operator for drivers, device plugin and DCGM, then a sharing layer chosen by workload. Time slicing advertises phantom replicas (Rafay flips an A10 between 2, 6 and 10 via a node label; vCluster runs 4 replicas on an RTX 5070 Ti) but gives no memory isolation, and Kubex watched a leaky classifier OOM-kill a neighbor LLM on a 24 GB L4. MIG carves an A100 into up to seven 1g.5gb slices with fault isolation, at the cost of static sizing. MPS, benchmarked by Klues and Chen, roughly doubles light-load utilization and, capped at 10% for low-priority work, holds near-dedicated performance. The split is throughput versus latency: Emmanuel Corels measured A100 throughput rising from 0.76 to 1.0 requests/s under MIG while time sharing kept mean latency lower.

## Section 1: The Practitioner Consensus

Every practitioner who actually ships shared GPUs starts from the same foundation: the NVIDIA GPU operator. Techi Nik frames its job bluntly — it detects GPU nodes, installs the NVIDIA drivers, manages GPU resources, and skips any node without a card, so mixed clusters stay clean [f-FKoMHqRoI @ 00:00:35]. Saiyam of vCluster lists the full payload the operator drops onto each GPU node: CUDA drivers, the container runtime, the device plugin, metrics, and GPU feature discovery [sXpJ4vSc-cM @ 00:31:46]. That discovery layer is what surfaces sharing to the Kubernetes scheduler. On Rafay's MKS cluster, the operator stamps nvidia.com labels onto the GPU node reporting GPU present true, an NVIDIA A10, a physical count of 1, and a time-slicing strategy with 10 replicas, so a single card shows up to the scheduler as ten [n-O8p7y9Z5A @ 00:00:44]. Jitesh Powankar calls enablement straightforward: install the operator, configure node policies, and once configured Kubernetes automatically discovers the new slices and reports them like CPU or memory [Ul1dZowvKvE @ 00:03:58]. The operator consensus is that nobody hand-rolls drivers and device plugins per node; the operator owns that layer, and every sharing strategy — time slicing, MIG, or fractional scheduling — is expressed as a label, a config, or an annotation that the operator and scheduler reconcile.

The business case is idle silicon. Jitesh Powankar puts numbers on it: a pod that requests a whole card may use only 20 to 30 percent, leaving 70 percent idle while other pods queue — like booking a whole 50-seat bus for one passenger [Ul1dZowvKvE @ 00:00:34]. The Code Architect drills into the hardware reason: a light task occupies about 10 percent of the streaming multiprocessors and the other 90 percent sit idle, because separate CUDA contexts cannot run concurrently, and an H100 is far more than a 256M-parameter model needs [TwICQ_zP8Ys @ 00:02:40]. Saiyam states the default outcome without a sharing layer: one pod takes the entire GPU, and no one else can use it until it releases it [sXpJ4vSc-cM @ 00:34:26]. The DevOps & AI Toolkit host hit that wall live on GKE: after llama 2 grabbed the single GPU with a limit of nvidia.com/gpu equal to 1, the second model sat Pending with no available GPUs, and buying another node only makes sense when the first is at full capacity — otherwise it is a waste of money [zuRKdveFuZ4 @ 00:08:47]. The shared conclusion: the default one-pod-one-card model burns budget, and the arbitrage is packing multiple tenants onto hardware you already pay for.

There is also broad agreement that no single mechanism wins; the mechanism has to match the workload. Kevin Klues frames it as space versus time partitioning, a fundamental inherent trade-off: MIG delivers full fault isolation and memory-bandwidth QoS but fixed partition sizes, while MPS offers flexible sizes with limited isolation that does not suit multi-tenancy [nOgxv_R13Dg @ 00:05:00]. Emmanuel Corels Academy describes the same split from the tenant's seat: time sharing lends idle capacity to other jobs but jobs compete when both are busy, whereas MIG gives isolated slices with no borrowing, so reserved capacity can sit idle [sRtvITK_o8I @ 00:00:52]. The Code Architect compresses it into a rule: time slicing for bursty heterogeneous workloads, MPS for trusted and predictable ones, MIG for absolute isolation [TwICQ_zP8Ys @ 00:08:03]. Core Concept Learning shows what that looks like across three teams on Run:ai: inference GPUs split into up to seven MIG instances, notebooks on Run:ai fractional GPUs, and large training kept on full GPUs, with the exam-grade advice to match the mechanism to the workload and each team's guarantee [56JbSXiXhhE @ 00:01:37]. Hardware gates the menu: The Code Architect notes MIG requires Ampere or newer, and Emmanuel Corels Academy flags the L4 as lacking MIG entirely.

## Section 2: Exact Street Mechanics, Tools & Numbers

Time slicing is a config-and-label game. Rafay's cluster runs a GPU blueprint (V2) mapped to an NVIDIA GPU operator add-on carrying time-slice configs for 2, 6 and 10 replicas; the engineer edits the node's nvidia.com label to profile six, saves it, and the operator reconciles 10 replicas down to 6 in a few seconds, then flips back to 10 when more applications need to land [n-O8p7y9Z5A @ 00:02:13]. The vCluster step-by-step runs the host side with GPU operator 25.3.0 and 4 replicas: create the time-slicing config, patch it, then describe the node to confirm 1 GPU advertising 4 replicas; inside each tenant vCluster with nodes enabled, reinstall the operator with the toolkit and driver disabled, reapply and re-patch, and expect a node refresh before 4 replicas appear [KzJvhbdgvl8 @ 00:01:27]. On GKE, Saiyam simply sets time-sharing with max shared clients per GPU at five on a single Tesla T4 and notes GKE automatically handles the operator install [sXpJ4vSc-cM @ 00:44:18]. Under the hood, Kevin Klues explains the device-plugin model: nvidia.com/gpu, GFD labels, a per-node replicas config such as 3, and a .shared suffix on the advertised resource [nOgxv_R13Dg @ 00:09:27]. Skip the replicas, the vCluster demo warns, and pods fail to schedule.

MIG is spatial and declarative. Rafay's upstream cluster shows a single A100 labeled MIG capable true; the blueprint layers an add-on setting the MIG single strategy, and because every partition is the same size the operator slices to the maximum the card supports — seven GPUs reported as GPU 0 through 6 [YoZoDn_Fvq0 @ 00:01:58]. A five-replica test app scheduled against all-1g.5gb nodes comes up with identical GPU UUIDs but distinct MIG UUIDs, which is the verification check. The DevOps & AI Toolkit host recreated a GKE node pool with partition 1g.5gb, which means one compute unit — 1/7 of the streaming multiprocessors — and 5 GB of memory, letting up to seven pods share one GPU so the stuck second model finally ran, while warning that sizing is dark magic best settled in the documentation, not by intuition [zuRKdveFuZ4 @ 00:10:19]. SUSE pushes MIG into VMs on Harvester 170: a MIG configurations CRD is auto-created by querying the driver, three profiles (1G.5GB, 2G.10GB, 3G.20GB) are defined, and each vGPU partition attaches to a VM [4q3LHacRheg @ 00:00:48]. Emmanuel Corels Academy lists the raw commands, nvidia-smi -l and nvidia-smi mig -l gip, and warns workloads need both GPU and compute instances, with some models requiring a reset [sRtvITK_o8I @ 00:01:38].

Fractional sharing with real memory enforcement is where the numbers get precise. Saiyam's KAI pattern is to annotate gpu-fraction 0.5 while keeping the resource limit at 1 [sXpJ4vSc-cM @ 00:38:38]. Julien Semaan of Kubex runs three workloads with gpu-fraction annotations of 0.35, 0.20 and 0.35 plus a reservation pod, but stresses KAI controls placement only; the fix is HAMi-core, which intercepts CUDA calls via LD_PRELOAD and converts a 0.35 fraction into an 8,061 MB CUDA_DEVICE_MEMORY_LIMIT, after which only the leaky classifier OOMs instead of the LLM beside it [Vw7DTM1SV60 @ 00:14:00]. The Code Architect applies the same discipline to Ray: a 0.25 GPU request only sets CUDA_VISIBLE_DEVICES, so vLLM's GPU memory utilization must be tuned to match the Ray placement fraction [TwICQ_zP8Ys @ 00:07:14]. Yuan Chen's benchmarks put MPS limits in hard figures: under heavy inference load, capping a low-priority job at 10 percent gives the high-priority job near-dedicated performance, and on GPU burn, where one job consumes about 23 to 24 GB and time slicing let job 1 take roughly 10 times job 2's memory, MPS with 50 percent limits fixed the imbalance, while the MPS daemon itself costs about 20 MB [nOgxv_R13Dg @ 00:20:02].

**SOP — Standard Operating Procedure**

1. Install and verify the GPU operator
   - Add the nvidia Helm repo, install gpu-operator with a values.yml setting the containerd template, socket path and nvidia runtime class, then run a test pod.
   - Run helm repo add nvidia and helm repo update, install into the gpu-operator namespace with --create-namespace --wait, confirm the driver daemonset, device plugin, DCGM exporter and toolkit pods come up after a couple more minutes, then kubectl exec a GPU count 1 TensorFlow pod and run nvidia-smi [Techi Nik — f-FKoMHqRoI @ 00:04:27].
2. Apply the sharing profile by label
   - Pick time-slice replicas or a MIG layout and drive it through the node label that the operator watches.
   - For time slicing, edit the node's nvidia.com label to a blueprint profile such as six or ten and let the operator reconcile the advertised GPU count in seconds; for MIG, let the GPU Operator's MIG manager apply a named configuration set through a node label [Rafay Systems — n-O8p7y9Z5A @ 00:01:29].
3. Enforce per-tenant memory at runtime
   - Pair fractional placement with a runtime memory cap so one tenant cannot OOM the card.
   - Annotate pods with KAI gpu-fraction values such as 0.35 and 0.20 for placement, then inject HAMi-core so the 0.35 fraction becomes an 8,061 MB CUDA_DEVICE_MEMORY_LIMIT via LD_PRELOAD and only the misbehaving pod OOMs [CNCF — Vw7DTM1SV60 @ 00:14:00].
4. Benchmark shared versus isolated and rebalance
   - Run identical jobs shared and on separate instances, ramp concurrency, and adjust layouts on a fixed cadence.
   - Give each job a distinct CUDA_VISIBLE_DEVICES, measure latency and throughput while ramping users, and remember nvidia-smi does not attribute utilization per instance, which is how an A100 at 50 users showed 0.76 versus 1.0 requests/s per GPU [Emmanuel Corels Academy — sRtvITK_o8I @ 00:02:25].

>

## Section 3: Where Practitioners Disagree & Alternative Playbooks

The first split is the classic one, time slicing versus MIG, and the practitioners do not land in the same place. Emmanuel Corels Academy ran the same jobs shared and then on separate MIG instances on an A100, with a distinct CUDA_VISIBLE_DEVICES per job, and at 50 users throughput moved from 0.76 to 1.0 requests per second per GPU, yet mean speech latency came in lower with time sharing [sRtvITK_o8I @ 00:03:35]. So the answer depends on whether a tenant is buying throughput or responsiveness. Julien Semaan of Kubex concedes in Q&A that MIG is usually faster but static, and his entire build targets making time slicing memory-safe rather than abandoning it [Vw7DTM1SV60 @ 00:20:40]. Kevin Klues frames it as a fundamental inherent trade-off: MIG buys full fault isolation and memory-bandwidth QoS but locks you into fixed partition sizes, while time partitioning gives flexibility that you pay for in contention [nOgxv_R13Dg @ 00:05:00]. The Code Architect settles the fight by workload class instead of ideology: time slicing for bursty heterogeneous workloads, MPS for trusted and predictable ones, and MIG only when you need absolute isolation [TwICQ_zP8Ys @ 00:08:03]. The operator read is that no single sharing mode wins every tenant mix, so each tenant gets placed and priced by the load profile it actually runs, not by whichever mode the platform team installed first.

Fractional GPUs split the field a second time, over whether a fraction is a promise or an enforced wall. Saiyam and Mike Peterson at vCluster demo the KAI approach: annotate the pod with gpu-fraction 0.5 while keeping the limit at 1 [sXpJ4vSc-cM @ 00:38:38]. Semaan warns that this controls placement only; KAI does not enforce the fraction at runtime, so noisy neighbors remain possible, and his fix layers HAMi-core underneath, intercepting CUDA calls through LD_PRELOAD so a 0.35 fraction becomes an 8,061 MB CUDA_DEVICE_MEMORY_LIMIT [Vw7DTM1SV60 @ 00:10:30]. The Code Architect hits the same wall from the Ray side: a 0.25 GPU request can still saturate the whole device because Ray only sets CUDA_VISIBLE_DEVICES, so the fix lives in the application, tuning vLLM's GPU memory utilization to match the Ray placement fraction [TwICQ_zP8Ys @ 00:06:22]. Yuan Chen's benchmarks push a third playbook, MPS with explicit limits: capping a low-priority job at 10% gave the other job near-dedicated performance under heavy load, where plain time slicing pinned the GPU at 100% and degraded badly [nOgxv_R13Dg @ 00:20:45]. Semaan's own talk counters that MPS adds a daemon that becomes another point of failure. The real choice is where enforcement lives: in the CUDA interception layer, in each application's memory config, or in an extra daemon on every GPU node.

The tenancy wrapper is the third fault line. vCluster's Saiyam and Mike Peterson argue namespaces provide weak isolation, you can't do CRDs, and 3,000 secrets in one namespace load etcd for everyone, so each tenant gets its own virtual cluster, with the host either syncing node information in or exposing only a runtime class [sXpJ4vSc-cM @ 00:41:50]. Core Concept Learning's Run:ai playbook stays in one shared cluster and runs it like a quota market: departments and projects hold guaranteed GPU quotas, research borrows analytics' idle GPUs overnight, and preemption claws the quota back when the owner returns [56JbSXiXhhE @ 00:00:56]. Luca Berton's OpenShift AI build for a French avionics customer is governance-heavy: tenants arrive through PR-based templates covering RBAC, network policies and quotas, while KAI caps, priority classes and preemption keep interactive work above training [nABVTFBmV2M @ 00:13:02]. SUSE moves the boundary down to the virtual machine, carving MIG-backed vGPUs in Harvester into 1G.5GB, 2G.10GB and 3G.20GB profiles and attaching each partition to its own VM, with both VMs seeing the GPU [4q3LHacRheg @ 00:00:48]. Each camp trades operational weight for a harder boundary: borrowing is light and fast, PR-gated templates leave an audit trail, and VM-attached partitions give the hardest line of the four. The operator picks the wrapper first, then picks the slicing mode that runs underneath it.

## Section 4: Firsthand Failure Modes, Traps & Economics Checks

Memory is where shared GPUs die first. Julien Semaan's Kubex demo put 5 time-slice replicas on a 24 GB L4, and nvidia-smi showed 13 GB for a pod whose real usage was 4 GB, so the standard tool misreported who was actually eating the card [Vw7DTM1SV60 @ 00:04:56]. Then a leaky classifier on the same GPU pushed LLM A into OOM, killing the well-behaved tenant instead of the offender. The Code Architect traces the same failure to layer misalignment: when hardware, driver and orchestration layers disagree, the result is OOM errors and node crashes, and Ray's fractional request only sets CUDA_VISIBLE_DEVICES, letting PyTorch and vLLM each grab the whole VRAM [TwICQ_zP8Ys @ 00:01:14]. Yuan Chen's GPU-burn benchmark quantified the imbalance: under plain time slicing, job 1 took about ten times job 2's memory, and only MPS with 50% limits evened it out [nOgxv_R13Dg @ 00:23:49]. Dynamia.ai's HAMi talk adds the utilization cost: without memory isolation, OOM crashes tanked utilization, and reserved memory, 5 GB in their example, is not the same thing as consumed memory, so unused reservations and noisy neighbors both have to be watched [zrGFmLHI7hg @ 00:09:22]. The economics check is blunt: an unenforced fraction is an outage waiting for the noisiest neighbor on the card, and it takes down the paying tenant first.

The second trap is capacity that exists on paper but never schedules. Jitesh Powankar frames the baseline waste: a pod requesting a whole card may use only 20 to 30 percent, leaving 70 percent idle while other pods queue, like booking a whole 50-seat bus for one passenger [Ul1dZowvKvE @ 00:00:34]. DevOps & AI Toolkit hit it live on GKE: after llama 2 took the single GPU, the second model sat Pending with no available GPUs, and adding another node before the first was at full capacity would have been a waste of money; recreating the pool with 1g.5gb partitions let up to seven pods share the card [zuRKdveFuZ4 @ 00:08:47]. vCluster's host-cluster walkthrough showed the inverse problem: without time-slicing replicas advertised, pods simply fail to schedule, so the replica count has to be confirmed on the node before tenants arrive [KzJvhbdgvl8 @ 00:04:26]. Gang scheduling is the costliest version: with 8 pods and 4 GPUs, the default scheduler places 4 and leaves 4 pending, so the job never starts while 4 GPUs are still consumed [sXpJ4vSc-cM @ 00:37:13]. DevOps & AI Toolkit also flags the quieter blocker: GPU nodes carry a NoSchedule taint, so a pod without the nvidia.com/gpu toleration never lands on the hardware you are paying for.

The third failure class is drift, and it hits the teams that are already winning. Saiyam warns that deleting the GPU operator leaves drivers on the node, and a reinstall then produces a version mismatch that just breaks [sXpJ4vSc-cM @ 00:01:22]. Luca Berton's air-gapped H200 build lost time to a ConnectX versus Intel RDMA kernel collision that blocked SR-IOV until the Intel driver was blacklisted, and the team's upgrade path now runs through a compatibility matrix in Git, a 48-hour canary pool and Argo CD rollback [nABVTFBmV2M @ 00:11:34]. Dynamia.ai reports that NVIDIA GPU operator updates very often change or break metrics, so metric pipelines have to be re-verified after every operator bump [zrGFmLHI7hg @ 00:10:03]. Core Concept Learning names the policy traps directly: static per-team GPUs, a whole GPU for every notebook, changing the MIG layout while work is running, and preemption without checkpointing [56JbSXiXhhE @ 00:02:19]. The payoff for avoiding them is real, with overall GPU utilization roughly doubling after a month of quota rebalancing, a MIG relayout on two drained nodes and coaching for idle-notebook users. Christian Kniep's checkpoint operator closes the preemption gap by restoring a PyTorch job at epoch 4 after the pod is deleted, for jobs carrying the checkpoint labels.
